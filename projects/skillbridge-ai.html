Case Study · Final-Year Engineering Project

SkillBridge AI

A multi-tenant platform that answers one question for a company: given who this person is today and where we need them tomorrow, what should they learn next? An AI pipeline reads the CV, measures it against a target role, proposes a learning roadmap — then stops and asks a human to approve it before spending another cent.

Part one · no technical background needed

What this is, in plain words

Every company has a gap between the skills it has and the skills it needs. Most discover it the expensive way — a project stalls, or a role sits open for six months. The usual fixes are a spreadsheet somebody maintains by hand, or a training catalogue nobody opens.

SkillBridge closes that loop automatically. An HR or L&D lead describes a role they need filled. An employee uploads their CV. The system reads both, works out precisely where the distance is, and produces a personalised learning plan with real courses, articles and videos attached to each step — plus a written explanation of why it recommended what it did.

The manager defines the target

Paste a job description. The system turns it into a structured role — the skills required, at what level, and why each matters. The manager edits anything it got wrong, then publishes it to the company. About ninety seconds, one AI call.

The employee gets their own plan

They pick a role they are working towards, upload their CV, and watch the analysis happen live. What comes back is not a score — it is an ordered plan, phase by phase, with learning material already attached and an estimated number of days.

The company sees the whole picture

A dashboard aggregates every analysis: how ready the workforce is for each role, which skills are missing most often across the whole company, and how far each person has progressed through their plan.

The part that matters most: it asks before it acts

Plenty of AI tools produce a plan and present it as final. This one deliberately stops halfway. Once the roadmap is drafted — but before it spends time and money hunting down learning resources for every step — the run pauses and shows the draft to the person it is for. They can reorder the phases, drop one, or reject it entirely with a note explaining what is wrong. Only then does the system continue.

Why this was a design goal, not a feature

A learning plan somebody did not agree to is a learning plan nobody follows. Pausing for approval costs the system a few seconds and saves it from confidently producing something useless. It also means every plan in the database has a human's decision attached to it — which is what makes the output defensible to an HR team, and auditable later.

And it shows its work

While an analysis runs, the screen is not a spinner. It is a live timeline of the actual steps — reading the CV, analysing the role, comparing them, drafting the plan, checking its own draft, searching for material. Each step reports whether it succeeded, and each learning resource is labelled with where it came from. If one source is unavailable, the interface says so rather than quietly returning less.

The three screens an employee sees

01

The Wizard

Before the run · light theme

Short and deliberately boring. Confirm the target role, upload or reuse a CV, optionally add a self-assessment, press start. Everything else is inferred, because the target role was already defined by the manager.

02

The Cockpit

During the run · dark mission-control theme

Full-screen, dark, and live. The timeline fills in node by node as the pipeline executes, streamed from the server as it happens. Small status indicators show which retrieval source answered for each phase. This is where the run pauses for roadmap approval.

03

The Workspace

After the run · light theme

The results, in three tabs: an Overview with the readiness verdict and a written narrative, a Gaps tab listing every skill and the distance to close, and a Roadmap where each phase can be marked in-progress or completed. A side panel replays the run's timeline for anyone who wants to see how the answer was produced. The full narrative exports as a PDF.

Built as a real product, not a demo

One deployment serves many companies at once. Each company's employees, roles and internal training library are completely walled off from every other company's — enforced at the database layer, on every single query, and covered by tests that try to break it. That isolation was designed in from the first schema, not retrofitted.

System architecture

A Next.js 14 app talks to a FastAPI service that owns the pipeline. Everything tenant-scoped hangs off a single company_id, and no endpoint ever accepts that value from the client — it comes from the JWT, always. Locally the whole stack runs on Docker Compose; in production the same code runs against managed equivalents behind four environment-variable switches.

LangGraph topology

The pipeline is not a chain. It opens with three independent branches from START, joins on a barrier, and later fans out again — one parallel branch per roadmap phase — through LangGraph's Send mechanism. Three of the eleven top-level nodes are themselves compiled subgraphs, which is what keeps the parent graph readable at 11 boxes instead of 26.

A race condition worth naming

profile_extraction originally depended only on ingest_documents. But its prompt injects the role's required skills, which come from job_analysis — so whenever job_analysis happened to be slower, extraction ran against an empty skill list and silently produced a thinner profile. No error, no exception, just a quietly worse answer. The fix is the multi-source edge above: ["job_analysis", "ingest_documents"] → profile_extraction. LangGraph treats a list source as a barrier, so the node cannot start until both have landed.

Inside the subgraphs

Gap analysis — draft, screen, then verify only what is doubtful

A single LLM call asked to grade twenty skills at once is confidently wrong on the borderline ones. Re-verifying all twenty is twenty times the cost for a handful of real corrections. So the subgraph splits the work: one structured-output call drafts every gap, a deterministic screener flags only the borderline items, and a single batched call re-verifies all of the flagged ones together. When nothing is flagged, the verification path is skipped entirely.

The subgraph carries its own GapSubState with private scratchpad fields — the draft, the uncertain items, the corrections. None of them ever surface to the parent PipelineState. LangGraph maps only the overlapping keys across the boundary: job_profile and user_profile in, gap_report and errors out. The parent graph has no idea this node has five steps.

Roadmap generation — a dependency graph, and a guard against the LLM's favourite failure

Phases are ordered by prerequisite, not by list position: one LLM call proposes a skill dependency map, pure Python turns it into ordered skeletons, and then Send fans out one generation call per phase. Two branches matter here — a stretch mode when there are no gaps at all (the person already meets the role, so the roadmap deepens existing strengths instead), and a short-circuit when stretch mode finds nothing worth deepening.

The dependency map has a known failure mode: asked which skills depend on which, a model will happily link everything into one serial chain — A → B → C → D — because the skills co-occur in the job, not because they are genuine prerequisites. That single line collapses an otherwise parallel roadmap into a strictly sequential one and inflates the estimate. So the map is validated before it is trusted, and rejected outright when it degenerates into a single spine with no branching: 

def _is_total_chain(dependency_map, skill_ids) -> bool:
    """One path through nearly every skill — a chain, not a DAG."""
    if len(skill_ids) < 3 or not dependency_map:
        return False
    if any(len(prereqs) != 1 for prereqs in dependency_map.values()):
        return False
    # A path visits each prerequisite once; a fan-out reuses one.
    prereqs = [p[0] for p in dependency_map.values()]
    if len(set(prereqs)) != len(prereqs):
        return False
    # One root, every other skill hanging off it.
    return len(dependency_map) >= len(skill_ids) - 1

The distinction it draws is the important part. A genuine fan-out — fastapi and django both requiring python — reuses a prerequisite, and is a legitimate DAG. A chain never reuses one. When the guard fires, the map is dropped and the phases stay independent, which is the safe default rather than the wrong one.

Reflect — repair structure first, spend attention second

Validation is staged by cost. A cheap deterministic structural check runs first; if it fails, only the offending phases are regenerated and the check runs again. The expensive LLM critique and the human's attention are never spent on a roadmap that is structurally broken.

The pause is a conditional interrupt, not a static one. reflect_human raises NodeInterrupt itself when review is needed, carrying the automated critique with it so the reviewer decides with the machine's opinion already in hand. Compiling with interrupt_before=[...] would have been simpler and wrong — it pauses on every pass, including the ones that need no human, and it breaks trace continuity in Langfuse.

Resumption goes through the checkpointer. The client POSTs the decision, the service injects it with aupdate_state(as_node="reflect_human"), and the graph continues from exactly where it stopped — same pipeline_id, same thread, same Langfuse trace. Because that state lives in a checkpoint rather than in process memory, a run survives a backend restart mid-review.

Retrieval: N parallel branches, then rank-fusion

Once a roadmap is approved, each phase gets its own branch. Inside a branch every retriever fires simultaneously under asyncio.gather — there is no sequential fallback — and each call is wrapped in safe_fetch(), which applies a timeout and swallows the exception into an ok: false flag. One dead API degrades a phase; it never fails a run.

SourceRoleRRF weight
exa_webNeural web search for articles, docs and courses1.5
exa_videoVideo-scoped search for the same query1.4
company_ragThe tenant's own Qdrant collection — internal training material1.3
tavily · youtube · llmImplemented behind the same ResourceRetriever interface; currently out of the active registry1.5 / 1.4 / 0.8

Results are fused with Reciprocal Rank Fusion rather than raw scores, because the sources produce incomparable numbers — a cosine similarity and a search rank do not live on the same scale. Two details in the config carry real intent: rrf_k = 10 is deliberately small, because per-source lists are short and a large k would let the weights dominate ordering instead of the ranks; and only company_rag has a relevance floor, because its scores are genuine cosine similarities in [0, 1] where 0.4 means off-topic — while a rank-based source's score encodes position, not magnitude, so flooring it would be meaningless. A URL-normalising dedupe collapses the same resource found by two sources, and a per-source cap of 2 stops any single retriever from owning a phase.

Engineering decisions worth defending

Every node fails softly, by construction

All nodes carry a @pipeline_node(name) decorator. It tracks per-node NodeStatus — which is what the Cockpit timeline renders — and catches exceptions into a NodeError appended to state rather than letting them crash the graph. The errors channel uses an append_errors reducer, so a partial run still reaches store_update and persists what it managed to produce. A run that fails halfway is still a run you can look at.

One write path, not fifteen

Nodes accumulate outputs in state; nothing touches the database until store_update. PipelineRunRepo.store_update() persists the target role, gap report, roadmap, resources and explanation report atomically at the end. The alternative — each node writing its own slice — would leave a crashed run as a half-written record that no reader could interpret.

The state is the schema

PipelineState is a TypedDict whose concurrency semantics are declared in the type itself. Because branches run in parallel, plain assignment is a lost-update bug waiting to happen, so the channels that multiple branches write to carry explicit reducers:

ChannelReducerWhy
errorsappend_errorsAny node in any branch may fail; all failures must survive.
staged_resourcesappend_batchesN parallel phase branches each return one batch.
node_statusesmerge_node_statusesConcurrent nodes report status simultaneously; last-write-wins would blank the timeline.
phasesannotated list appendThe Send fan-out reduces N phase results into one channel.

Concurrency is capped on purpose

The graph config sets max_concurrency from settings. Without it, a wide fan-out — parallel gap verification plus one retrieval branch per phase — issues a burst of LLM calls that trips the provider's per-minute limit, and the resulting stack of 429 retry-backoffs makes the run slower than if it had never parallelised. Parallelism past the provider's ceiling is negative work.

Prompts are versioned artifacts

PromptManager loads .txt templates carrying a front-matter version header, applies str.format(), and caches the rendered string in an LRU dict — with the version as part of the cache key. Editing a template therefore invalidates its cached renders automatically, which removes the entire class of bug where a prompt change appears to do nothing.

Model access goes through one factory

Nodes never import a LangChain chat class. LLMFactory is the only place that knows which provider is in play, which is what made two provider-specific problems into one-line fixes rather than ten-file refactors. LangChain's with_structured_output() defaults to json_schema, which Groq's llama models reject outright — so a mixin injects the correct method provider-wide instead of at ten call sites, with an explicit caller argument always winning. The primary model is Groq llama-3.3-70b with a Gemini fallback wired through .with_fallbacks().

Tenant isolation is structural, not a code review habit

The rule

No endpoint accepts company_id from the client — ever. It is read from the JWT, injected as a dependency, and used as a filter on every tenant-scoped query.

The mechanism

get_current_user() returns a CurrentUser value object; require_admin() wraps it and raises 403 on role mismatch. Cross-tenant reads return 404, not 403 — 403 confirms the resource exists, which is itself a leak.

The vector store follows the same rule: one Qdrant collection per company, named company_docs_{company_id}, so a retrieval query cannot cross a tenant boundary even if the filter were wrong — there is nothing to cross into.

Fitting a torch-shaped stack into 512 MB

Local development runs twelve containers. Production runs on a free 512 MB / 0.1 CPU instance. Closing that gap was profiling work, and each fix is an environment-variable switch whose default reproduces the Compose behaviour exactly — so docker compose up is untouched.

All six now route through one storage module.

Observability

Langfuse auto-instruments every node through the callbacks key in the graph config. Each run is one trace tagged with user_id and pipeline_id, so a trace can be correlated with its database row directly. Because checkpointing keys on pipeline_id, resuming a run continues the same trace rather than starting a second one — nodes that already executed do not reappear. Underneath, structlog emits JSON with a request_id bound per HTTP request by middleware, and the graph exposes GET /topology, which renders its own live structure as a PNG straight from the compiled graph — so the diagram can never drift from the code.

Document ingestion

Library uploads are handled off the request path: the file lands in object storage, an ARQ job is enqueued, and the worker downloads, parses, chunks, embeds and upserts. Embeddings are generated locally with fastembed — BAAI/bge-small-en-v1.5, 384 dimensions — which means no per-document API cost and no third party seeing a tenant's internal training material. The worker retries up to three times and marks the row failed on permanent failure, so a stuck document is visible in the admin UI rather than silently absent from search results.

Limitations

Stated plainly, because a case study that hides them is not worth reading.

  • No golden-dataset evaluation of gap accuracy yet. The screening and verification stages measurably reduce borderline errors, but there is no labelled set scoring gap severity against ground truth — which is exactly why this page quotes no accuracy figure.
  • The free-tier demo sleeps. Instances idle out after fifteen minutes, so the first request after a quiet period pays a cold start.
  • Retrieval quality is bounded by the sources. Web search returns what it returns; there is no editorial layer scoring whether a course is actually good, only whether it is relevant.
  • English only. Prompts, parsing and the UI all assume English CVs and job descriptions.
  • Roles are mutually exclusive in v1. A person is either an admin or an employee within a company, never both. A manager tier with team-scoped visibility is designed but deferred.
  • The human gate is optional in practice. An employee can approve a roadmap without reading it. The gate guarantees a decision was recorded, not that it was considered.
