Case Study

Medical Agentic System

Multi-agent clinical question answering over a temporal knowledge graph. An LLM router decides how much machinery each question deserves before any work begins — and the entire reasoning pipeline, every agent and every tool call, streams to the browser as it runs.

CrewAI Neo4j + Graphiti Gemini 2.5 Flash FastAPI + SSE React 19
Live Demo API Docs View on GitHub

Overview

3 specialised agents, activated per query
1–5 complexity score driving the plan
11 typed trace events streamed live
3 retrieval sources, fused and scored
512MB total memory budget in production

A question is routed by a model before any work begins. The router decides whether the question is medical at all, how complex it is, which of three agents to activate, how many tool iterations each one gets, and whether the answer needs explicit step-by-step reasoning. A definition lookup runs one agent against one source. A multi-drug safety question runs three agents across a knowledge graph, generated Cypher, and web search.

The browser shows that decision as it happens: the routing verdict, each agent activating, every tool call with its measured latency, and each reasoning step as it lands.

Design thesis

An agent system you cannot watch is one you cannot debug, and one nobody should trust. Every architectural decision here serves two properties: the work is proportional to the question, and the reasoning is observable from outside the process. The trace is not a debug log bolted on afterwards — it is a first-class output, produced by instrumenting the tools directly rather than depending on framework callbacks.

The public demo caps each visitor at five queries per day. The example questions are pre-computed and exempt from that limit, so the system can be explored without spending the allowance.

System architecture

Two Render services: a static React bundle and a single-worker FastAPI container. The split is deliberate — static sites consume none of the free tier's 750 instance-hours, which leaves the entire budget for the API, and the interface paints instantly while the backend is still cold.

The AI engineering

The framework work is the least interesting part of this system. What follows is the engineering that makes an LLM pipeline behave like a service rather than a demo.

Routing is a typed contract, not a classification

One deterministic call at temperature=0 returns a JSON plan that everything downstream obeys. Routing with a model rather than keyword matching is the whole point: "can I take these two together" and "is this combination safe" need identical handling, and no keyword list captures that. The model's output is parsed into a validated dataclass, with every field clamped — complexity to 1–5, agent names to a known set, iteration budgets to integers with defaults. Nothing downstream ever sees free text. 

QueryAnalysis(
    is_medical=True,
    intent="interaction",
    complexity=4,
    confidence=0.95,
    required_agents=["researcher", "validator", "analyst"],
    max_iterations={"researcher": 5, "validator": 3, "analyst": 1},
    suggested_tools=["graph_db", "cypher", "web_search"],
    use_chain_of_thought=True,
    cot_reasoning_steps=["identify each drug's mechanism", "…"],
    reasoning="Multi-drug analysis; safety-critical, needs validation",
)

The router costs one cheap call and saves running three agents on a question that needs one. It is also the only component that must never hard-fail. If the routing call errors, it falls back to a conservative configuration that runs the full crew — a wasted crew run is cheaper than wrongly refusing a legitimate clinical question. Non-medical queries are refused at the router, before any expensive work is scheduled.

Two execution topologies, chosen by the plan

The router's output selects between two fundamentally different shapes of work:

  • Sequential crew — CrewAI agents run in order, each one's output becoming the next one's task context. Researcher gathers, validator grades severity, analyst writes for a non-specialist. Agent count and per-agent iteration caps come straight from the plan.
  • Parallel retrieval — every relevant source is queried concurrently under asyncio.gather with a hard 20-second ceiling, each result is confidence-scored, and an LLM merge step cross-references them and is instructed to state disagreement explicitly rather than paper over it. Selected when complexity ≥ 3, two or more tools are suggested, and the intent is an interaction check — the only case where several sources will agree or disagree usefully.

Observability: the trace comes from the tools, not the framework

Each tool publishes tool_started / tool_completed — with elapsed milliseconds, cache status, and success — to a request-scoped event bus held in a contextvars.ContextVar. Any code on that context can publish without being handed a reference, and when no sink is bound, publishing is a no-op, which keeps the same tools usable from tests, scripts, and the non-streaming endpoint with no special-casing.

This is deliberately independent of CrewAI's internals, which are not a stable API. It also forced a real concurrency fix: CrewAI executes synchronously in a worker thread, and context variables do not cross run_in_executor on their own, so the pipeline copies the context explicitly. Without that copy, every tool event raised inside a crew run is silently dropped and the UI shows a blank pipeline while the answer works perfectly. 

ctx = contextvars.copy_context()
return await loop.run_in_executor(None, lambda: ctx.run(_kickoff))

The sink itself is written so that a broken trace can never take down the query it describes: emitting is thread-safe via call_soon_threadsafe, and a closed or shut-down loop drops the event instead of raising.

Chain of thought as structured data

When the router flags a question as safety-critical it supplies 3–5 concrete reasoning steps, and a separate processor works the findings through them. An earlier version formatted the reasoning into markdown and prepended it to the answer, which meant the interface could only render a wall of text. Each step is now emitted as its own typed event with a name, reasoning, and conclusion, so the UI renders reasoning as it arrives and the answer itself stays clean. The parser is deliberately tolerant: a malformed model response still yields an answer.

Both /ask and /ask/stream call one run_query implementation, so there is exactly one description of what happens to a question. The only difference between the two endpoints is how the trace is delivered.

Retrieval and the knowledge graph

Medical entities and their relationships live in Neo4j, with Graphiti layering temporal GraphRAG on top — hybrid vector and graph search fused by reciprocal rank, reranked by a Gemini cross-encoder over 768-dimension embeddings. Three retrieval paths sit above it:

  • Hybrid graph search for entities the graph is likely to know — returns extracted facts, falling back to entity summaries when edges are thin.
  • Generated Cypher for multi-hop traversals the hybrid search cannot express: every drug interacting with warfarin, all contraindications for a condition.
  • Web search for recent or rare drugs outside the seeded dataset, labelled as such in the trace.

Both cache layers are keyed with intent. The response cache normalises word order, so "aspirin warfarin interaction" and "interaction warfarin aspirin" resolve to one entry — but it is scoped per session, because answers depend on conversation context. The tool cache has a subtler rule: a graph-unavailable result is deliberately never cached. Storing a degradation would pin the fallback in place for an hour after the database came back.

Safety and reliability engineering

Generated Cypher is treated as untrusted input

Cypher is written by an LLM from user text and then executed against the database, so a prompt-injected DETACH DELETE is a live risk, not a theoretical one. Every generated query passes a write-clause denylist — covering mutations, procedure calls, and apoc/dbms namespaces — is rejected if it contains multiple statements, and is then executed with explicit read routing and a hard timeout. Both controls, because either alone is one bug away from a wiped graph. 

@staticmethod
def reject_if_unsafe(cypher: str) -> str | None:
    """Return a reason when the generated Cypher is not a plain read."""
    if not cypher or not cypher.strip():
        return "empty query"
    match = _WRITE_CLAUSE.search(cypher)
    if match:
        return f"non-read clause '{match.group(0).strip()}'"
    if ";" in cypher.strip().rstrip(";"):
        return "multiple statements"
    return None

A rejection is itself a trace event — the guard firing is visible in the UI, not buried in a log.

The graph degrades instead of failing

The demo runs on Neo4j AuraDB Free, which pauses after a few days idle. All graph access goes through a gateway that owns a single long-lived client, verifies connectivity on connect, tracks availability, and refuses to retry inside a 30-second cooldown — so one paused database cannot add a connection timeout to every subsequent request. Callers ask for a client and get None when the graph is unusable; tools then return an explicit signal, and the agents are instructed to answer from web search while stating that graph verification was not possible. Degrading silently would be worse than failing.

Runtime engineering

All graph work runs on one dedicated event loop

Neo4j's async driver binds its internal locks to the loop that opened the connection pool, and this process has several: the request loop, plus a fresh one per asyncio.run() inside tools that CrewAI invokes synchronously from worker threads. Sharing a cached client across them fails with <AsyncRLock> is bound to a different event loop — and because graph tools degrade rather than raise, that failure is invisible: the agent quietly answers from web search and the response still looks fine. The fix is structural: one long-lived loop in a background thread owns every graph coroutine, with sync and async submission helpers on top.

The provider was chosen by measurement, not preference

The system began on Groq and moved to Gemini for two concrete reasons found by running it. Graphiti's entity-extraction prompts reach roughly 19k tokens per episode against a 12k tokens-per-minute ceiling on Groq's free tier — a single oversized request, which no amount of pacing or retrying can satisfy. Separately, CrewAI 1.x marks cache breakpoints on agent messages and strips them only for providers it supports natively; Groq is not one, so those messages reach the API carrying a property it rejects, and every crew run fails. Both providers stay selectable through AGENT_LLM_PROVIDER and GRAPH_LLM_PROVIDER for anyone on a paid tier.

Fitting an agent system into 512MB

The original sentence-transformers embedder pulled in torch — roughly 2.5GB of image and over 500MB resident, against a 512MB deployment ceiling. Moving embeddings to an API call was the difference between deployable and not. The same budget shapes the rest: sessions are an LRU-bounded registry capped at 200 conversations of 40 messages, injecting only the last six turns into a prompt; the response cache evicts its oldest entry at 500. A related trap was fixed by being explicit — Graphiti silently defaults an unset cross-encoder to an OpenAI reranker, which demands a key this deployment does not have and fails only in production, on any machine where that variable happens to be set locally.

Delivery

Render's auto-deploy is switched off on purpose: its default is to deploy on every push, which bypasses CI entirely and would happily ship a red build. Deploys are triggered by GitHub Actions only after tests pass, and the deploy job then polls /health until the new revision answers.

WorkflowTriggerPurpose
ci.ymlpush, PRRuff lint and format, pytest, frontend typecheck and build, Docker build plus a live container health check
deploy.ymlCI success on mainCalls both Render deploy hooks, then waits for /health
keepalive.ymlevery 10 minutesPings /health, keeping the instance and AuraDB Free awake

Seven test modules cover the pure logic and every path that resolves before a model or database call — the Cypher guard, the event bus across thread boundaries, cache keying, quota accounting, reasoning parsing — so the whole suite runs in CI with no API keys at all. The Docker job boots the image with GRAPH_ENABLED=false and curls /health, which proves the container starts and serves with no database and no model keys: exactly the condition Render's health check imposes.

Limitations

Stated plainly, because a system that hides them is not one worth trusting.

  • Not medical advice. This is an engineering demonstration. The graph holds a small curated drug dataset, not a clinical knowledge base, and no clinician reviews the answers.
  • No evaluation suite. Routing accuracy is unmeasured. A labelled set scoring intent and complexity against ground truth is the obvious next step — and its absence is precisely why this page quotes no accuracy numbers.
  • State is per-process. Sessions, the response cache, and the rate limiter all live in memory and reset on restart. Redis is the production answer; it is not free.
  • Single instance. One worker on 512MB. The rate limiter assumes this and would need a shared store before scaling out.
  • Cold starts. The free tier sleeps after fifteen minutes idle. The keep-alive ping covers this, and the UI reports honest progress when it does not.
  • Answer quality is bounded by the graph. Drugs outside the seeded dataset fall through to web search, which is less reliable — and is labelled as such in the trace.
